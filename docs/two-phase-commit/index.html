两阶段提交

一笔转账要同时改两个数据库,要么都成功、要么都回滚——跨机器的「都」字怎么保证?两阶段提交(2PC)的答案是把决定权收给一个协调者:第一阶段「准备」,协调者问所有参与者「能提交吗」,每个参与者把 undo 日志写进磁盘后回答 yes 或 no——yes 是带后悔药的承诺:从此刻起它能提交也能回滚,但必须停住等第二阶段;第二阶段「提交」,协调者只要收到全票 yes 就广播 commit,所有参与者正式生效;任何一张 no 或超时,广播 rollback,大家 undo。协议本身简单,恶名在故障模式:最毒的一刀是「参与者投完 yes 后协调者失联」——参与者已锁定资源,不能单方面提交也不能回滚(它不知道别人投了什么),只能卡在 in-doubt 状态死等协调者苏醒,锁不释放,整条业务线排队;这正是 Raft/Paxos 一类共识协议与「协调者高可用」要解决的问题。第二毒是协调者在写 commit 记录前宕机——重启后读日志就能续发决定,所以「先写日志再发消息」是 2PC 的命根。代价清单:一次提交至少两次往返、每个参与者多一次 fsync,延迟是单机的三倍以上;MongoDB 4.0+、TiKV 的 Percolator 变体等分布式数据库都内置了它的变形。拖「故障时机」看每种宕机发生在哪一步,拖「节点数」看消息轮数;按「正常提交」看两幕完整流程,按「参与者宕机」看 in-doubt 阻塞,按「协调者宕机」看日志恢复续发,按「中止回滚」看 no 票引发的全员 undo。3D 交互演示 · 鼠标拖动旋转 / 滚轮缩放 · 空格播放/暂停

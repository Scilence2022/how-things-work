HyperLogLog 基数估计

统计「十亿访客里有几个不重复的用户」,精确数法要一个装十亿 ID 的哈希集合——几个 GB 内存;HyperLogLog 用 12 KB 做同样的事,误差约 2%,它的洞察只有一句:均匀随机的哈希值里,「前导零的个数」携带基数信息。一个集合基数越大,出现「一长串前导零」的哈希值的概率就越大——看到 k 个前导零,基数大概率在 2^k 量级。单次观测噪声太大,LogLog 的办法是分桶平均:用哈希值的前几个 bit 把元素分到 m 个桶(比如 16384 个),每个桶只记一个数字——该桶见过的最大前导零数;最后用调和平均把所有桶的估计聚合起来,调和平均对离群桶不敏感,这正是选它的原因。HyperLogLog 再修两处偏差:小基数时的线性计数(空桶太多就直接数)与大基数时的偏差修正表,把误差压到约 1.04/√m,且无需存任何元素本身。工程上它是 Redis 的 PFADD/PFCOUNT、Google 的 PowerDrill、各家数据库的近似 COUNT(DISTINCT)——所有「UV 统计、独立访客、不同卡片数」的海量场景,本质都是在「精度 2%」与「内存 12 KB」之间做交换。反方向姊妹是布隆过滤器:那个回答「见过没有」,这个回答「见过几个」。拖「元素数」看估计曲线贴合真值,拖「桶数 m」看误差与内存的交换;按「散列入桶」看前缀分流,按「寄存器更新」看最大前导零,按「调和估计」看聚合公式,按「对比精确」看内存差距。3D 交互演示 · 鼠标拖动旋转 / 滚轮缩放 · 空格播放/暂停

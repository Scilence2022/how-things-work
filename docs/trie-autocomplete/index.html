前缀树与自动补全

你在搜索框打出 "apr",候选词 0.1 秒内浮现——这背后不是在十万词条里做模糊匹配,而是一棵前缀树(trie):每个节点是一个字符,从根到节点的路径就是前缀。"apr" 三个字符走三步落在一个节点上,查询成本只跟词长有关、与词库大小无关——十万词和一亿词都是 3 步。哈希表查一个词同样快,但它把前缀信息全打碎了:以 "ap" 开头的词散落在桶的四面八方,想找「所有 ap 开头的词」只能全表扫描;前缀树则把共同前缀收拢成同一条路,走到节点后收下整棵子树,前缀查询变成一次下行的顺路收获。候选词再按使用频率排序:每个节点存一个计数器,历史查询把高频词顶到建议前列——这就是搜索框前三名的来历。代价是内存:字符级分叉产生大量稀疏节点,工程上用压缩路径(radix tree,把单链压缩成一条边)或双数组 trie 压到可承受;路由器还发明了同构用法:IP 路由表按二进制位建前缀树,查 200.100.5.x 时取「最长前缀匹配」——/24 的专网路由优先于 /8 的默认路由,互联网每天靠这棵树转发百亿亿个包。拖「查询词」看树的下行路径点亮,拖「词库规模」看查询步数纹丝不动;按「线性扫描对照」看朴素搜索的多慢,按「IP 路由」看最长前缀匹配,按「压缩前后」看节点数坍缩。3D 交互演示 · 鼠标拖动旋转 / 滚轮缩放 · 空格播放/暂停
